# Plan — skills-v2: measure what matters, then improve what the data points at
**Weight:** Standard (sliced; S1 spends API money, so it needs the owner's go-ahead)

## Outcome
Every skill in the suite has measured evidence or an explicit "unmeasured" label. Paired
evals separate skilled from unskilled runs on every task kind, because no task sits at the
1.00 ceiling any more. The skills change where the data shows a gap:
- `shipify` gets a fast path and a parallel-work reference;
- `reviewify` and `traceify` get the missing rules the field reports asked for;
- routing is back to 100%.

Field feedback records cost and a concrete catch, so the dashboard shows what a helped run
bought, not only that the agent said "helped".

## Scope
- In:
  - paired-eval harness (`scripts/run-paired.mjs`);
  - new fixtures in `evals/paired/`;
  - new results in `evals/results/`;
  - `skills/shipify`, `skills/reviewify`, `skills/traceify`, `skills/orientify` (description only);
  - `scripts/log-feedback.mjs`, `scripts/feedback-report.mjs`, `dashboard/`;
  - routing cases in `evals/*.json`;
  - README "Does it help?".
- Out:
  - new skills;
  - agents' frontmatter model choices;
  - skills that are not ours (`prototype`, `animate`, …);
  - teachify's interactive quality (it needs a human learner and can't be auto-graded honestly);
  - renaming anything.

## Requirements and invariants
- R1: Every coding and debugging fixture used for claims has a Sonnet no-skill mean ≤ 0.85,
  with n=3, so a skill can show gain.
- R2: `shapeify`, `promptify`, `releaseify` and `audify` each have at least one paired fixture with results.
- R3: Paired results record the resolved model id (for example `claude-sonnet-5-5`) and tokens,
  not only the alias and dollars.
- R4: `shipify` on a trivial one-file task costs at most 15% more than no skill, while scores stay equal.
- R5: `shipify` has `references/parallel.md` covering worktree per worker, ports and control ports,
  starting and stopping test servers, rebuilding before screenshots, and what counts as visual proof.
- R6: Routing evals pass 100% on `claude` with Sonnet 5.5 and Haiku.
- R7: Field entries can carry `catch` (one concrete thing the skill caught, or "none"). The dashboard
  shows catch rate and cost per helped run next to the verdict split.
- R8: README and the dashboard's Overview headline are regenerated from the new results. No
  hand-typed numbers.
- I1: Existing results files are never edited in place except for documented regrades. New runs go to a new
  dated folder.
- I2: `node scripts/validate.mjs` passes after every slice. Descriptions stay ≤ 2800 B in total.
- I3: Skills stay harness-agnostic: no Claude-only instruction in a SKILL.md body. Model-specific
  guidance lives only in `promptify/references/`.

## Constraints and priorities
Honest evidence > coverage > polish.
- A fixture that can't be graded reliably is dropped, not softened.
- Money: S1 calibration plus S2 runs are estimated at about 170 paired runs on Haiku and Sonnet
  (≈ $15–25) plus DeepSeek (≈ $2).
- Stop and ask before exceeding $30.

## Evidence
- [FACT] Coding and debugging fixtures are at the ceiling: all three models score 1.00 without skills on
  `debug-memo`, `feature-discount`, `refactor-utils`, and Sonnet/DeepSeek on `feature-softdelete`.
  Source: `evals/results/2026-09-28`, dashboard Evals matrix.
- [FACT] Measured gains exist only for rubric tasks: undumbify (Haiku +73 pts), reviewify (Haiku +27).
- [FACT] Skills cost +8–48% per run on those ceiling tasks. Sonnet's cost per score point is +38% with skills.
- [FACT] Field verdicts: 39/39 skill runs "helped", 6/6 no-skill runs "neutral". They are self-reported,
  so the concrete catches cited in the text are the stronger evidence.
- [FACT] The most frequent "missing" ask (5 runs) is conventions for parallel workers: worktrees, ports,
  test servers and visual proof.
- [FACT] Only 4 of 35 field entries record tokens.
- [FACT] Routing: `traceify/feature-not-bug` routes to `orientify` with Sonnet 5.5 (19/20 pass).
- [FACT] `run-paired.mjs` stores `opts.model` (the alias) and `cost`, not the resolved model or tokens
  (lines ~96–126).
- [ASSUMPTION] Harder multi-file fixtures will pull Sonnet below 0.85 without skills. Breaks if Sonnet
  still aces them; checked by P2's calibration.
- [ASSUMPTION] `shipify`'s cost on trivial tasks comes from ceremony (baseline, plan, full verification)
  that a fast path can skip. Checked by P7.
- [DECISION] Measure `promptify` by outcome, not prose: a brief written with or without promptify is
  handed to a fixed Haiku executor, and the hidden tests grade the executor's work. Rules out grading
  prompt style with a rubric.
- [DECISION] `teachify` stays unmeasured and is labelled so. Rules out a rubric on lesson text, which
  would reward form over teaching.

## Steps

### S1 — Measurement that can show gain (needs owner go-ahead for spend)
- P1: Record the resolved model and usage in `scripts/run-paired.mjs` → the row object near line 124:
  - `modelId` = the first key of `meta.modelUsage`;
  - `tokens` = input + output + cache tokens from the same object.
  - Default `--out` to `evals/results/<today>/r1-<model>.jsonl`, and refuse to overwrite an existing file.
  - [BATCH]. Depends on: none.
  - Verify: `node scripts/run-paired.mjs --task debug-memo --reps 1 --arms base --model haiku --out /tmp/x.jsonl`
    → the row has `modelId` and `tokens`.
  - Trap: the CLI's `modelUsage` keys differ under `ds-claude`; take them as reported.
- P2: Add three harder fixtures, each with hidden tests and a `note` naming its traps:
  1. `evals/paired/feature-audit-log`: a feature touching 5+ files, with two readers that bypass the obvious path.
  2. `evals/paired/debug-race`: an intermittent failure from a shared cache between two request paths, whose
     symptom fix passes the visible tests.
  3. `evals/paired/migrate-config`: a config-format migration where one consumer is dynamic.

  Then calibrate: run each with `--arms base --reps 3` on Sonnet. Keep a fixture only if its mean is ≤ 0.85;
  otherwise add a trap and re-run, at most twice.
  - [ISOLATE]. Depends on: P1.
  - Verify: each kept fixture's calibration mean is ≤ 0.85.
  - Fails if: after two revisions a fixture still scores > 0.85. Drop it and log why.
  - Trap: making a fixture "hard" with an ambiguous prompt. The difficulty must come from the code, and
    the prompt must stay a fair ticket.
- P3: Run the full paired set on the new fixtures plus the old ones:
  - Haiku and Sonnet: 3 reps each.
  - DeepSeek via `--cli ds-claude`, with the grader on Codex.
  - Output goes to `evals/results/<date>/`.
  - [BATCH]. Depends on: P2.
  - Verify: the dashboard build (`cd dashboard && bun run build`) shows the new tasks. No run is marked
    invalid; re-run any that are.

### S2 — Evidence for unmeasured skills
- P4: `evals/paired/plan-export` (shapeify, rubric). The prompt asks for a plan to add CSV export touching
  3 modules. Rubric items:
  - names real files and symbols;
  - gives each step a check;
  - names at least 2 traps that are present in the repo;
  - writes no code.

  Scoring = items ÷ 4, minus 0.2 if the plan invents a file.
  - [BATCH]. Depends on: P1.
  - Verify: one manual grading pass agrees with the Codex grade within 0.15 on 2 answers.
- P5: `promptify` outcome eval. Add a `--stage brief` mode to `run-paired.mjs`:
  - the arm model writes a brief for a fixed task (reuse `feature-audit-log`), with or without promptify loaded;
  - a fixed Haiku executor gets only the brief;
  - the hidden tests score the executor's result.
  - [ISOLATE]. Depends on: P2.
  - Verify: one full run per arm completes. Both briefs and both scores are recorded.
  - Trap: letting the executor see the original ticket. It must see only the brief.
- P6: `evals/paired/release-notes` (releaseify, rubric). The repo has 9 commits: 1 breaking, 1 fix,
  1 feature, and the rest chores. Rubric items:
  - picks a major bump;
  - the changelog lists the breaking change first;
  - there is a rollback line;
  - chores are omitted.

  Also `evals/paired/audit-service` (audify, rubric) with 4 planted issues: a secret in config, no health
  check, an unbounded log, and a missing backup.
  - [BATCH]. Depends on: P1.
  - Verify: calibration as in P2. The Sonnet base mean is ≤ 0.85, or the fixture is labelled "no headroom".

### S3 — Improve the skills where the data points
- P7: `shipify` fast path in `skills/shipify/SKILL.md`. Add a first section, "Weight": a one-file change
  with an obvious check gets a short path (read, change, run the check, report). The full procedure only
  applies from two files, or any unclear check. Keep SKILL.md ≤ 4500 B.
  - [ISOLATE]. Depends on: P3 (a baseline cost to compare against).
  - Verify: paired run on `feature-discount` (the trivial one), Haiku and Sonnet, 3 reps. Skill cost is at
    most 1.15× base and scores are unchanged. `feature-audit-log` scores don't drop.
  - Fails if: the harder fixture's skill score drops by more than 0.05. Revert the wording and try a narrower trigger.
- P8: `skills/shipify/references/parallel.md` (≤ 3200 B), linked from SKILL.md, covering:
  - a worktree per writer, with absolute paths and shared deps by symlink;
  - a port range per worker, including control ports;
  - starting test servers detached and stopping them by port (`ss -ltnp`), never `pkill -f`;
  - rebuilding production bundles before screenshots;
  - visual proof: viewports, both themes, and looking at every screenshot you cite;
  - checking `git status` for another writer's files before staging.

  Keep it harness-agnostic, with no Claude-only commands.
  - [BATCH]. Depends on: none.
  - Verify: `node scripts/validate.mjs` passes. `grep -c "worktree" skills/shipify/references/parallel.md` ≥ 1.
- P9: Rules the field asked for:
  - `reviewify`: "verify claims about third-party tools by running their help or version output", and
    "a narrow, non-security residual Material finding may be approved when named".
  - `traceify`: "if the reported repro passes, say so, look for adjacent defects that fit the symptom,
    and label the cause as unconfirmed".
  - [BATCH]. Depends on: none.
  - Verify: validate passes, and the budgets hold.
- P10: Routing fix. Diagnose `traceify/feature-not-bug` first: run
  `node scripts/run-evals.mjs --adapter claude --model sonnet --case feature-not-bug --repeat 3` and read the
  chosen skill's reason. The likely fix is `orientify`'s description, adding "not for feature requests".
  Re-run all routes on Sonnet 5.5 and Haiku.
  - [ISOLATE]. Depends on: none.
  - Verify: 20/20 plus the new promptify cases pass on both models.
  - Trap: overfitting the description to one prompt. Add one more feature-request routing case before
    changing the text.

## Acceptance
- A1: `evals/results/<date>/` holds rows with `modelId` and `tokens`. The dashboard lists the new fixtures.
  Proves R3.
- A2: Every coding and debugging fixture cited in README has a Sonnet base mean ≤ 0.85 in the data.
  Proves R1.
- A3: The dashboard Tasks view has at least one fixture each for shapeify, promptify, releaseify and audify.
  Proves R2.
- A4: `feature-discount` skill/base cost ratio ≤ 1.15 on Haiku and Sonnet, with equal scores. Proves R4.
- A5: `skills/shipify/references/parallel.md` exists and validate passes. Proves R5, I2, I3.
- A6: Routing evals 100% on Sonnet 5.5 and Haiku. Proves R6.
- A7: The dashboard shows catch rate and cost per helped run. The last 5 field entries have both. Proves R7.
- A8: README numbers equal the dashboard's. `scripts/readme-evidence.mjs` reproduces them. Proves R8, I1.

## Stop conditions
- Projected spend passes $30, or any single fixture's runs pass $5.
- A grader (Codex) is rate-limited: mark runs invalid and wait. Never score them 0.
- A fixture can't reach ≤ 0.85 after two revisions: drop it, don't loosen the grading.
- A skill change drops any measured score by more than 0.05: revert it and report.
- A budget in `validate.mjs` would need raising: ask the owner first.
